A workflow lets application code choose the sequence of work. An agent lets a model choose some of the next steps. Pick between them by asking how much of the process you can specify in advance, then test whether the extra flexibility improves the result.

Suppose a small software company wants help with incoming support tickets. The first request sounds broad: "Use AI to handle support." That could mean labeling a ticket, drafting a reply from documentation, or investigating a customer's account across several systems. Those tasks need different amounts of control. Giving all of them an autonomous agent would skip the most useful design question: what work actually requires a changing plan?

## Start with an answerable task

Take a narrow version first. Given a ticket and the relevant product documentation, draft a reply for a support person to review. A single model call might handle that. The application can retrieve the documentation before the call; "one call" refers to the generation step, not to an application with no other code.

At **Start simple**, write down what a successful draft must contain. For a password-reset ticket, it should identify the documented reset procedure, avoid requesting the customer's password, and explain the next action. If the output fails because the prompt omitted the procedure, fix the missing context before adding a planning loop.

Read the top lane as a choice about control. Follow **One call enough?** toward either **One model call** or **Predictable steps?**. The lower lanes compare the consequences of adding a workflow or an agent.

## Predictable work can still contain model calls

Now suppose the company wants to classify tickets, fetch documentation for their category, and draft a reply. The sequence is known even though the wording of each ticket differs. **Predictable steps?** leads to **Code-led workflow**.

Application code can require classification before retrieval and refuse to draft when no relevant document is available. Different models could perform classification and writing, but the code determines when those calls happen. A workflow therefore does not mean "no AI." It means that the process follows predefined control decisions.

The **Predictable process** node names the benefit. A support engineer can inspect which stage failed and decide what to retry. The cost is that an unexpected ticket may not fit the available branches. For example, a billing issue mislabeled as a login issue can receive the wrong documents unless the workflow provides a fallback or review path.

That limitation may be acceptable. A visible "needs human review" result can serve customers better than an assistant improvising account operations it was never designed to perform.

## When the process must adapt

Consider a different support task: investigate why a scheduled export did not arrive. One customer may have no completed export; another may have a completed export with a failed notification. The next useful lookup depends on the evidence returned by the previous one.

Here, **Model-led agent** may fit. The model can choose whether to inspect job status, account settings, or delivery records. The application still defines available tools, enforces authorization, and limits execution. Model-directed control does not grant permission to access every account or retry forever.

**Flexibility and cost** captures the tradeoff. A changing investigation can answer cases a rigid sequence misses, but it may require more model calls and more waiting. It can also pursue an irrelevant explanation. These are reasons to evaluate the design, rather than reasons to assume either approach always wins.

## Decide with the same cases

At **Measure outcomes**, run candidate approaches on the same representative support cases. Check whether they resolve the actual question, use evidence correctly, and stop when information is missing. Record response time and resource use alongside quality. An impressive demonstration of one unusual case does not establish that an agent improves everyday support.

Include ordinary tickets as well as ambiguous investigations. Otherwise, the evaluation may reward flexibility while ignoring the slower answers it imposes on simple requests. Keep cases where a correct result is a clarification or an escalation; forcing every case into an automatic resolution rewards overconfident behavior.

The **Better outcomes?** decision sends a failed comparison back to **Start simple**. That does not require abandoning all model use. It may mean narrowing the task, improving retrieval, or keeping only the workflow stages that helped. The **Yes** branch reaches **Keep it simple**, meaning retain the least complicated design that earned its place. It does not mean an agent that passed evaluation must become a single call.

The drawing does not explicitly connect the one-call branch to the measurement loop. Evaluate that baseline too. Without a baseline, you cannot tell whether added orchestration helped.

Choose a workflow when you can name the steps and their failure behavior. Consider an agent when the evidence must determine the next step. In either case, the support customer's outcome is the reason to add complexity.
