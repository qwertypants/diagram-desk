An agent's model can propose a tool call. The application decides whether to execute it, runs the permitted operation, and returns the result for another model decision. That division lets an assistant investigate a question without giving every generated instruction authority over your systems.

Imagine a signed-in customer asking, "Where is order 4821? It was supposed to arrive yesterday." A language model cannot know the current delivery status from its training. It needs a lookup. The question is how to turn that need into a useful answer while preserving the customer's access limits.

## A request becomes a proposed action

The diagram starts at **User Request**, passes through the **API** to the **Orchestrator**, then reaches **Load context** and the **LLM**, the large language model. The orchestrator is application code that manages the conversation and its calls to the model.

In our example, context includes the customer's question and the definitions of available tools. A tool definition tells the model what an operation does and what arguments it accepts. We might offer `get_order_status` with an `order_id` argument. The model can then propose `get_order_status` with order `4821`.

This is a structured request to application code. It has not contacted the order database yet. Anthropic's [client-tool documentation](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview) shows this separation between the model's tool-use output, application execution, and a returned tool result. Provider-hosted tools have a different execution owner; this diagram illustrates application-managed tools.

Start with the request row, follow **Need a tool?** down its **Yes** branch, and trace the result back to the model. Then compare that loop with the **No** branch that leads toward the customer.

## Permission belongs at execution

**Need a tool?** describes a decision about the next step. It is not a security approval. The **Tool Router** dispatches a proposed operation to its implementation. In this example, the router and tool handler must check the request before allowing the **Database** lookup.

Two questions matter. Is `4821` a valid order identifier? Is this signed-in customer allowed to read that order? An argument can have the right format and still identify someone else's order. The tool handler must use the authenticated session to enforce ownership; a customer identity generated by the model cannot establish permission.

These checks belong in ordinary application and downstream access controls. The chart does not draw a separate authorization service. Its router and tool implementations are where this example needs enforcement. OWASP's [excessive-agency guidance](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/) recommends narrow tool capabilities, limited permissions, and authorization outside the model.

For this task, a read-only order lookup is enough. Offering unrestricted SQL or a refund operation would give the assistant capabilities the delivery question does not need. If permission fails, the application should return a denial without the protected order details. Asking the model to "respect privacy" cannot replace that check.

## Why the result goes around again

Suppose the database returns a carrier tracking number and a last-known status of "dispatched." That is a successful lookup, but it does not yet answer whether the parcel is delayed. **Tool Result** therefore returns to **LLM**. The model may propose a second lookup through **External API** using the tracking number.

The other branches, **Search / RAG** and **Code / Compute**, represent available capabilities, not compulsory stops. Retrieval-augmented generation, or RAG, retrieves documents to supply context. It might help explain a delivery policy, but policy text cannot establish this parcel's location. Running every tool would add work without answering the customer's question better.

Now imagine the carrier returns "delayed at depot" with an update time but no delivery estimate. The model has enough to explain the delay. It should preserve the missing estimate rather than inventing a new arrival date. A tool result can be incomplete or stale even when the call succeeds.

## Finishing includes failure

On the **No** branch, **Generate response** produces an answer and **Validate response** checks it before returning it to the user. For our example, a useful check asks whether the answer's status, update time, and delivery estimate agree with the returned records. Those response checks happen too late to authorize an operation that has already run.

If the carrier API times out, a good outcome might be, "Your order has shipped, but I couldn't confirm its current location." The application can return a tool error as feedback and allow a bounded retry. Repeating the same failing lookup indefinitely gives the customer neither a better answer nor a timely response.

Set limits in the orchestrator for tool rounds, elapsed time, or cost. For example, an illustrative policy could allow one carrier retry before ending with the verified information and the unresolved question. Reaching a limit means the investigation stopped; it does not mean delivery status was confirmed. The chart omits these stopping branches, so treat them as required implementation decisions rather than visible guarantees.

The dashed connections to **Trace + evaluate** record what happened across orchestration, model decisions, and routing. A useful trace distinguishes "lookup denied," "carrier unavailable," and "answer returned." That distinction helps explain a failure without confusing a proposed call with one that ran.

## When the loop earns its complexity

If every request follows the same order lookup and carrier lookup, a fixed workflow can call them directly. A model-directed loop becomes useful when the next step depends on what the previous result reveals, such as choosing between tracking a parcel and explaining a delivery policy. Each extra round adds waiting time, cost, and another opportunity for a wrong decision. Anthropic's [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) explains this tradeoff and recommends explicit stopping conditions.

Before building the loop, decide what counts as enough evidence to answer, which operations the customer may authorize, and what the user will hear when evidence stays incomplete. Those choices determine whether a delivery assistant can finish responsibly.

This is an illustrative architecture and hypothetical support scenario, not a running delivery integration.
