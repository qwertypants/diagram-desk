The useful boundary is where a proposed action becomes an actual tool call. The model can request one; application code decides whether it runs.

## The problem

A support assistant needs internal data and external tools without treating model output as executable authority.

## Read the architecture

Start at the request, follow one tool decision out and back, then locate the checks before the answer leaves the system.

### Walk through it

#### 1. Request and context

The API hands the request to the orchestrator, which loads context before calling the model.

#### 2. Tool routing

A tool decision selects the database, retrieval, external API, or compute capability. Results return to the model for another decision.

#### 3. Response and evidence

A no-tool decision produces a response. Guardrails run before returning it; tracing observes the agent, model, and tools.

## Design decisions

- Keep tool execution in application code so tool arguments can be checked.
- Trace the complete loop, including failed calls and stopping reasons.

## Failure modes

- A repeated tool loop needs an iteration and cost budget.
- Response guardrails alone cannot authorize a side effect.

## Key takeaways

- Tool results are feedback, not a guarantee of correctness.
