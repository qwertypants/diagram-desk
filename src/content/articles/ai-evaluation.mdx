An evaluation turns "is this AI system better?" into a set of tasks with inputs, expected behavior, and a way to judge the outcomes. Production traces help choose those tasks, but a log of what happened does not by itself tell you whether the behavior was good.

Imagine a documentation assistant that answers questions about a software product. A proposed prompt update makes its answers shorter. Before releasing it, the team wants to know whether those shorter answers still explain required migration steps. The desired improvement is not simply fewer words. It is less reading without losing instructions users need.

## Specify what a case asks

Live **Traffic** reaches the **AI app**, which calls the **LLM** and produces a **Response**. Under an explicit data policy, **Traces** record enough context to inspect the behavior. For our assistant, that might include a request identifier, the prompt version, retrieved document identifiers, timing, and the answer.

The team samples a migration question where the new prompt omitted a restart step. **Sample cases** turns that observation into evaluation material. Before storing customer content, remove secrets and decide what data may be retained. A trace collection should not become an unrestricted copy of every user conversation.

**Golden cases** supplies a curated set of inputs with reviewed expectations. "Golden" means useful as a reference, not eternally correct. If the product's migration procedure changes, the expected behavior must change too. Version the cases and expectations so a comparison has a clear meaning.

Our example case asks how to migrate a particular configuration. Its supplied documents contain three required actions. The success criterion requires all three, prohibits unsupported actions, and permits a concise answer in different wording. Requiring an exact paragraph would reject valid explanations for the wrong reason.

## Different questions need different graders

**Evaluation** sends work through **Rules**, **Model judge**, and **Human review**. These paths provide complementary evidence. They need not each grade every aspect of every case.

Use rules where the property has a clear mechanical answer. A rule can check that cited document identifiers exist, or that a structured response contains the required fields. It cannot establish that a free-form migration explanation is safe merely because the answer contains the word "restart."

A model judge can compare the answer to a rubric and source material. For the migration question, ask whether it covers the required actions without inventing extra ones. Calibrate the judge against expert-reviewed examples, including polished answers that omit a critical step. Otherwise, a score may reflect writing style more than task success.

Human review handles ambiguous cases and checks whether the criteria represent real user needs. If two reviewers disagree about whether a restart is necessary, resolve the documentation or rubric question. Averaging their disagreement into a number conceals the problem.

Keep each criterion visible in **Results**. A single composite score can make a shorter answer look better while hiding a drop in migration completeness.

## Read results as a release decision

At **Dashboard**, compare the baseline and candidate on the same cases. Separate routine lookup questions from migration questions and questions with insufficient documentation. A stable overall score can hide a failure in a smaller but consequential category.

The **Regression?** decision sends **Yes** to **Revise candidate**, then back to evaluation. A revision might restore the instruction to preserve mandatory steps. Run the unchanged cases again and inspect whether the fix also affects answer length or introduces unsupported detail.

The **No** branch reaches **Deploy**. Read that as permission under the chosen acceptance policy, not proof that no future failure can occur. The chart compresses the judgment into one question. A real policy should also require the candidate to meet absolute quality criteria; being no worse than a poor baseline is insufficient.

Because model behavior can vary, a single successful run is weak evidence for an unreliable case. Repeat important trials where variation matters and report failures as well as averages. Keep a held-out set of cases so repeatedly adjusting a prompt to the visible examples does not become the only measure of success.

This loop is useful when prompts, models, retrieval, or tools change. Start with a small reviewed set that represents the task, then expand it with meaningful failures. The goal is a release decision that can explain which user outcomes improved and which risks remain.
