An AI feature still depends on ordinary product boundaries: identity, state, jobs, and operational evidence. The model is one component among them.

## The problem

An interactive product also needs authentication, durable jobs, model routing, and evidence about quality.

## Read the architecture

Follow a protected request from the gateway through application state into AI execution, then inspect the separate background path.

<DiagramEmbed slug="ai-product" title={'Full AI product architecture'} />

### Walk through it

#### 1. Application boundary

The client reaches the gateway. Authentication must succeed before the application service handles protected work.

#### 2. AI execution

The orchestrator builds prompts, retrieves indexed context, and invokes permitted tools. A model gateway selects a provider.

#### 3. Background and feedback

The application queues background jobs; workers call the orchestrator. Application, model, and tool traces feed evaluation.

## Design decisions

- Keep the model gateway separate from application authorization.
- Persist business state in the application database rather than relying on model memory.

## Failure modes

- Fallback providers may have different tool and context contracts.
- A queue acknowledgement does not prove that a job completed.

## Key takeaways

- Each dependency adds an ownership and failure boundary.
