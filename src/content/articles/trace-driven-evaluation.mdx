A trace explains one request; an evaluation asks whether a change improves many representative tasks. Both are needed to investigate a regression.

## The problem

Users report worse answers after a model update even though the average dashboard score is stable.

## Read the architecture

Move from the observed failure to a fixed case, then compare candidates by segment.

### Walk through it

#### 1. Observe the request

Propagate trace context across retrieval, model, and tool operations. Record errors and token usage while applying content-redaction policy.

#### 2. Build the evaluation

Select representative failures and add them to a fixed dataset. Replay the candidate model or prompt against the same tasks.

#### 3. Review the change

Compare task success, latency, and cost by segment. Inspect failures and human-calibrated judge results before promoting or holding the release.

## Design decisions

- Traces diagnose behavior; they do not replace a task rubric.
- Token usage is observed data; monetary cost also needs a dated provider price model.

## Failure modes

- Sampling only easy requests misses rare severe failures.
- An LLM judge can reward convincing but incorrect answers.

## Key takeaways

- Keep the inputs and grading criteria stable when comparing candidates.
