Two valid actions can disagree without one being disposable. When a dispatcher reassigns a job while a technician completes it offline, the system must decide what each action means. A version mismatch identifies concurrency; the business rules determine whether completion, assignment, or both should stand.

Imagine technician Maya repairing a heater assigned to Truck A. Her tablet loses connectivity. While she finishes the repair, a dispatcher moves the job to Truck B because the office has not received an update. Maya records completion with the repair time and a note. On reconnect, the server sees a newer assignment and an older-based completion.

## Preserve both actions before reconciling

At **Job scheduled**, the workflow splits into two writers. In **Dispatch transaction**, **Move A to B** leads through **One transaction** to **Supersede A; B live** and **Write outbox**. Treat the visible sequence as changes within that transaction's boundary: the assignment update and its event intent must agree.

An outbox is a durable record that an event needs delivery, committed with the business change. AWS's [transactional outbox guidance](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html) explains why independently saving a change and sending a message can leave the systems inconsistent. Here, a later delivery failure should not erase the office's assignment or the intent to notify clients.

Meanwhile, **Complete offline** reaches **Write local store**, then **Queue durable action**. Maya's tablet stores the fact and the pending submission locally. Her note should survive closing the app before reconnect. The interface can acknowledge that it is saved locally while clearly showing that server acceptance is still pending.

Trace the two upper lanes independently before following reconnect. Their actions occur without seeing each other; the bottom lanes resolve that disagreement.

## Catch-up is different from a notification

**Wake-up fan-out** has a dashed **Wake-up only** connection to **Pull after cursor**. A wake-up tells a client to check for changes. It is not the durable change history itself. If Maya misses the notification, reconnect should still let her pull events after the last position she processed.

A cursor is a saved position in that event stream. After **Reconnect**, the tablet uses it to obtain newer server changes, then **Send completion** submits the locally recorded action. Reading the latest assignment helps explain the conflict, but should not silently delete the technician's pending fact.

The completion request needs an action identity and the version on which Maya acted. If the response disappears, she can resend the same logical action. **Check key + version** can recognize an already processed submission and return its recorded outcome. A fresh identity on every retry would defeat that recognition.

The diagram does not specify the event storage, cursor expiry, or local database. A real offline application needs recovery for a cursor that is too old and clear ownership checks for submitted actions. Those omissions do not change the central concurrency decision.

## A whole-record overwrite loses meaning

The server reaches **Field-level check**. In this illustrated policy, the job's completion status has not changed since Maya's base version, so **Status unchanged** permits **Accept completion**. The newer assignment is retained separately through **Retain assignment** and **assignment changed**.

Why retain an assignment that is now stale? Because it records the dispatcher's real action and lets the system resolve it explicitly. Accepting Maya's entire older record could revert Truck B to Truck A without explanation. Rejecting her entire completion could erase useful evidence of work that actually happened. Neither whole-record outcome captures both actions.

The server records **Status complete** and **Append audit event**. The audit event should preserve who completed the work, when it was recorded, the submitted note, and the conflict decision. This is an example domain policy: it assumes the completion remains acceptable despite reassignment. A safety-critical dispatch system might require different validation or human acceptance before changing status.

## Close the operational disagreement

Both the completion audit and the retained assignment lead to **Create review item**. The dispatcher can inspect why Truck B is still assigned to completed work, then **Close B assignment**. **Completion stands** means Maya's accepted work remains recorded while the unnecessary follow-up dispatch is closed.

The review item is operational work with an owner. Merely logging a conflict would leave Truck B's driver uncertain about whether to travel. Define who sees the item and what happens until it is resolved; the diagram does not make notifications or human response instantaneous.

Also distinguish this case from two competing completions or a cancelled job. The chart's acceptance branch depends on unchanged status. A different status conflict needs another rule, rather than automatically applying this example's result.

This design is useful when people must act during disconnection and concurrent changes affect different responsibilities. If offline edits are unnecessary, requiring a current server decision before completion is simpler. When offline operation is essential, keep action identities, durable local facts, and field-specific policy together. The heater repair is hypothetical, and the chart describes one chosen reconciliation policy.
