A model can return an object that fits a schema and still make the wrong decision. Use structured output to make the response parseable. Then let application code check the facts and authority before a side effect.

Consider an illustrative refund assistant. A customer asks for a refund on order 42. The model proposes `{ "order_id": "42", "eligible": true, "reason": "late delivery" }`. The JSON parses and every field has the expected type. Yet the order may belong to another customer, or the refund window may have closed. The schema answers whether the object has the expected **shape**; it does not establish eligibility.

Read the diagram left to right. **User request** asks **Model** for a classification. **Schema parser** checks the returned form. **Policy check** reads trusted order state and customer identity. Only then does **Application** decide whether to approve, reject, or escalate.

## Make the contract narrow

Ask the model for the smallest useful proposal: order reference, proposed category, and a short explanation. Use an explicit enum for the category and reject unknown values. OpenAI's [Structured Outputs guide](https://developers.openai.com/api/docs/guides/structured-outputs) distinguishes a structured final response from function calling, which connects a model to application tools. As of October 2026, the supported schema subset and refusal behavior remain provider-specific; pin and test the exact API contract in use.

A parser failure, refusal, or incomplete response should be an explicit outcome. It must not silently become `eligible: false` or `eligible: true`. The first hides a service failure; the second risks an unauthorized refund. A retry can be bounded to one attempt for transient formatting errors, followed by human review or a clear error.

## Check authority against trusted state

The **Policy check** loads order 42 using the authenticated customer's scope. It computes eligibility from stored delivery and payment facts. The model's explanation may help route a case, but it does not override those facts. OpenAI's [function calling guide](https://developers.openai.com/api/docs/guides/function-calling) describes tool arguments as model-produced data that application code executes. Validate those arguments at the operation that uses them.

For verification, test a valid object with an order owned by another customer, a closed refund window, a refusal, and malformed output. The first two must stop before the refund API. Log the decision category and policy result without storing unnecessary customer text. If the task is a read-only summary, a plain answer may be simpler than a schema and policy pipeline.
